轻量本地视频 Agent
设计文档：评审、架构与人在回路

基于《本地接管试验报告（已核对）》与《轻量本地视频 Agent · 实施计划》。Telegram + 自建服务为主入口，确定性编排器掌握一切副作用，LLM 按需唤醒，OpenClaw 作为可调用的子 agent。

1. 背景与范围

结论：用本地 27B 模型做“控制面”、ComfyUI 做“执行面”的方向可行，但目前只证明了最容易的一环（读事实写报告）。真正的风险点——自主改工作流、视频端到端、生成峰值内存——全部未验证。建议先把 LLM 从关键路径上拿掉，做一个确定性的编排器，再把 LLM 作为可选的规划器接入。

本文依据《本地接管试验报告（已核对）》和《轻量本地视频 Agent · 实施计划》（计划稿，尚未实施）。第 2 节对计划逐项评审，其余章节是在评审基础上的设计建议。

试验已确认的事实

  • OpenClaw 用 lmstudio/qwen3.8-27b-splash 单次 agent exec 成功，耗时 85.2 秒，退出码 0，无 --deliver、无付费兜底。
  • ComfyUI 队列查询、空闲时 /free 释放、忙队列拒绝释放的逻辑已验证；/free 后进程 RSS 约 9.3 GiB → 0.82 GiB。
  • 机器总内存 128 GiB；ComfyUI 报告可用约 58.9 GiB，/free 后系统可用约 54 GiB（受其他进程干扰）。
  • 工具隔离在 workflows/openclaw-local-media，未改全局配置、未装常驻组件。

本文不覆盖：具体模型选型与量化方案、ComfyUI 节点级调参、OpenClaw 数据库的 SQLite 警告修复。

2. 对实施计划的评审

计划的核心判断是对的：以模型调度器为中心、确认释放、只动自己的模型、从获准定妆出发、最终审美由人决定。主要问题有三个：范围偏大，实际是在重建一个 OpenClaw；严格错峰会让每轮迭代背上多次模型加载，和快速选版冲突；最大的未知（视频峰值内存）排到第 3 阶段才验证。

计划做得好的地方

  • 状态机把“释放控制模型”“释放生成模型”写成显式状态，并要求结合内存观测确认释放，不只信接口返回。
  • 模型所有权与“尊重手动任务”两条，正好覆盖本文 Concern #5 的竞态问题。
  • 保存 ComfyUI job ID 用于重启恢复，避免重复生成。
  • 候选图区分“临时试验”和“用户批准的定妆”，每轮从获准基准出发，与本文的导演基准包一致。
  • 每阶段都有完成标准；隔离做法（独立目录、虚拟环境、数据库，先手动启动）稳妥。

3. 可行性分析

总体判断：有条件可行。“串行 + API 驱动 + 模板化参数”这条路技术上没有障碍；“LLM 自主修改并提交工作流”和“LLM 与视频模型常驻共存”是两个需要实测才能下结论的条件。

维度结论置信度依据与缺口
编排技术（ComfyUI API）可行高/prompt、/queue、/history、/free 均为标准接口，队列与释放逻辑已实测；工作流 JSON 按节点 ID 改参是确定性操作
LLM 控制面（27B）文本任务可行；自主改工作流未知中→低只验证了“读事实写报告”；27B 本地模型直接编辑节点图易出错（错节点 ID、类型不符、越界参数）
内存共存未知，可能偏紧低128 GiB 统一内存，后测可用约 54 GiB；LLM 权重实际占用未测；视频模型峰值未测；虚拟机约 14.7 GiB 常驻
时延批处理可接受，交互不可接受中单轮 LLM 85.2 秒；多轮 agent 循环每任务额外数分钟；Mac 上视频生成本身也以分钟计
稳定性未知低仅一次成功运行；CLI 有 SQLite 维护警告；无长期运行数据
成本边际成本为零高无付费兜底；代价是只能串行、吞吐低

内存粗算（近似值，未实测）：27B 模型在 Q4 量化约 16–18 GiB、Q8 约 28–30 GiB；报告原文“BF16 占 54 GiB”已被标为未验证。若 LLM 用 Q8 常驻，加上虚拟机与系统开销，留给视频模型的空间可能只有 30–40 GiB，足够 640×384 短视频但不宽裕。这正是需要第一个实测的数字。

4. 主要 Concern

最大的三个风险：LLM 处在每一步的关键路径上、内存共存没有实测、视频链路从未端到端跑通。

#Concern严重度缓解措施
1LLM 在关键路径：每轮约 85 秒，且输出不确定；让 27B 模型直接改工作流 JSON，容易写错节点 ID、类型或越界参数高LLM 产出的参数或工作流变体先经图校验与低档试跑，再进入生产
2内存争用：LLM、视频模型、虚拟机同时驻留，macOS 进入内存压力后大量 swap，整机变慢甚至 ComfyUI 崩溃高提交前做内存门控；LLM 按需加载、空闲卸载；记录每次峰值
3视频链路未验证：640×384、3 秒模板从未端到端执行，生成峰值内存和耗时都是空白高把“视频冒烟测试”列为第一个里程碑的退出条件
4安全边界靠提示词：“不关应用、不改配置、不下载模型”目前只是约定，agent 有 exec 能力就有越界可能高用工具白名单强制：只开放编排器的几条命令，不给通用 shell
5释放缓存的竞态：检查队列为空到发出 /free 之间，用户可能手动提交了任务中释放前二次确认队列；只释放本系统加载的模型；或由用户触发
6失败恢复缺失：生成中途失败、超时、ComfyUI 重启后，没有任务记录，可能重复提交或丢结果中每个任务一个持久化记录（状态、prompt_id、参数），提交前查重
7可观测性不足：没有记录参数、种子、耗时、峰值内存，结果无法复现，也无法调参中每次任务写一份 manifest.json，和产物放在一起
8OpenClaw 自身：SQLite 维护警告、网关约 3.7 GiB 常驻、临时状态与日志，版本升级可能改变行为中锁定版本；把 OpenClaw 当按需调用的子 agent，而不是系统核心
9身份一致性：是否需要因任务而异，效果也未验证中需求澄清时询问；需要时作为任务级约束（定妆参考图 + 一致性评分）挂到模板上，架构不变；效果仍需实测
10前提污染：原始报告的未验证推断（机型、BF16 占用、回退成本为零）可能被后续计划沿用低每个数字标注“实测/估算”，估算项列入验证清单

5. 高层设计建议

核心建议：把系统拆成“确定性编排器 + 可选 LLM 规划器”。编排器负责一切有副作用的操作，LLM 只负责把自然语言需求翻译成受约束的方案；没有 LLM 时系统照样能跑。

设计原则

  • 确定性优先：提交、轮询、释放、重试全部由 Python 代码完成，LLM 不直接接触 ComfyUI API 或 shell。（2026-11-07 修订：agent 可以请求执行命令、读网页、读写文件、用 skill，由编排器执行；命令每条经用户批准，生成相关副作用仍只走生成工具。）
  • 受控探索：agent 可以探索不同的模板、模型和工作流，但所有新组合都要先过校验与低档试跑，生产任务只用已晋升的模板。
  • 内存是一等资源：每次提交前检查可用内存，LLM 与生成模型分时使用，不追求同时常驻。
  • 每个任务可复现：参数、种子、模板版本、约束配置、耗时、峰值内存写进 manifest，与产物同目录。
  • 最小权限：越界行为在工具层被拒绝，而不是靠提示词约束。

探索机制：分级的受控探索

agent 的探索范围按风险分五级，越往下护栏越重。前四级 agent 可以自主进行，只有“晋升为正式模板”和“引入新资源”需要人确认。

层级agent 能做什么护栏需要人确认
L1 参数改 prompt、种子、采样器、步数、CFGschema 范围约束否
L2 模板在模板库中选择、组合模板模板注册表，标注能力与适用场景否
L3 模型在本地已有的 checkpoint、LoRA、VAE 间切换模型注册表记录大小与实测峰值内存；提交前内存门控否
L4 工作流增删节点、改连线、编写新工作流按 ComfyUI /object_info 校验节点类型与连线；最低档试跑；输出写入沙盒目录晋升为正式模板时需要
L5 新资源下载模型、安装自定义节点沿用试验报告的约束：默认不下载、不装常驻组件每次都需要

新工作流的生命周期：候选 → 图校验 → 最低档试跑 → 评估 → 人工确认后晋升进模板库。每次探索都写一条实验记录（模板、模型、改动、耗时、峰值内存、结果评分），agent 下次探索先查这份记录，避免重复踩坑。

探索要设预算：每轮限定试跑次数或总时长，因为 Mac 上一次视频试跑就以分钟计，加上 27B 每轮约 85 秒。结果评估是待定点：人工打分最可靠，用视觉模型自动评分则会再占一份内存。

按需唤醒：LLM 不常驻，收到消息才启动

常驻的只有一个不加载模型的消息监听器。命令和按钮由它直接处理；只有需要理解的自由文本才加载 LLM，处理完进入空闲计时，到期卸载。这样人随时可以介入，又不占内存。

消息类型例子唤醒 LLM处理方式
命令/status、/cancel、/pause、/budget否监听器直接执行
按钮选择选中 2 号、打回、混合 1+3否写入审阅结果，触发锁定或下一轮
自由文本批注“眼神再忧伤一点，光打侧面”是理解成参数改动，经校验后提交
新需求“用这个定妆照做回头镜头”是先澄清关键选项（是否要求身份一致、时长、风格），再规划任务
  • 冷启动会慢：加载 27B 要读入整份权重，再加上推理（实测一轮 85.2 秒），一条自由文本可能要一两分钟才有回复。监听器先秒回一句“收到”。
  • 空闲计时避免反复加载：连续的几条消息共用一次加载；计时长度按 G0 测得的加载耗时来定。LM Studio 的按需加载与空闲自动卸载能否按实例生效，待第 0 阶段核实。
  • 加载期间到达的多条消息合并成一次处理。
  • 不抢占生成：生成占着内存时自由文本排队；“停”“取消”这类紧急指令是命令，监听器立即执行，不必等 LLM。若 G0 显示内存有余量，可允许 LLM 与生成并存。
  • 上下文从数据库重建：每次唤醒读取项目摘要、基准包和近期记录，不重放全部聊天。
  • 后台探索同理：调度器在需要规划下一轮时才唤醒 LLM；用户消息优先于后台探索的下一轮。

驻留模式：可选，默认按需唤醒

LLM 的驻留方式做成可切换的选项。切换用命令 /mode，由监听器直接执行，不需要 LLM；也可以给每个项目设默认值。

模式LLM 行为适合场景代价
按需唤醒（默认）收到自由文本才加载，空闲到期卸载日常使用、长时间挂着每次冷启动要等一两分钟
会话常驻用 /session 开启后保持加载，结束或超时卸载密集选版、连续批注会话期间占内存，生成要与之共存或排队
始终常驻一直加载，响应最快内存充裕、追求即时回复持续占用；视频生成时可能被临时卸载
纯命令不加载 LLM，只用命令和按钮生成高峰、内存最紧时无法理解自由文本，文字消息只排队

内存门控优先于模式设置：当生成任务需要的内存放不下常驻的 LLM 时，调度器临时卸载 LLM，并通过 Telegram 告知用户；生成结束后按原模式恢复。

OpenClaw 作为可调用的子 agent

已定：主入口是 Telegram + 自建服务，调度权在编排器。OpenClaw 降为编排器按需调用的子 agent，承担不想自建的能力（搜索、现有 Skills、MCP）。评审问题 #1 的范围膨胀因此基本化解。

方面做法
调用方式编排器发起单次 agent exec（试验已验证：85.2 秒、退出码 0、不用 --deliver）；输入是结构化任务说明，要求输出文本或 JSON
交给它的网络搜索与资料整理、复用已有 OpenClaw Skills、需要 MCP 的操作
不交给它的提交 ComfyUI、释放内存、改模型或配置、写项目记忆；这些只在编排器里发生
资源调用前占用资源锁，因为它也走 LM Studio 的 27B；尽量与本服务共用同一个已加载的模型实例
结果处理输出当作数据，经 schema 校验后才进入参数或记忆；调用记录写入 manifest
失败处理设超时；非零退出、超时和 SQLite 警告都记录，有限次重试后向用户汇报
网关OpenClaw 网关实测约 3.7 GiB 常驻；能否按需启停、调用后退出，待第 0 阶段核实

6. 目标架构

两个入口汇入同一个编排器；LLM 规划器是可选件；Telegram 和 LLM 都碰不到 ComfyUI 或 shell，OpenClaw 由编排器按需调用。

一个任务的生命周期：草稿 → 已校验 → 等待内存 → 已提交 → 生成中 → 待审阅 → 完成 / 打回 / 失败 / 超时。每次状态变化都写回 manifest，进程重启后按 prompt_id 去 /history 对账，避免重复提交。

编排器对外只暴露四条命令：plan（可选，调 LLM 出参数）、submit（校验并提交）、status（查任务）、release（空闲时释放）。Telegram 监听器只能调用这四条命令；OpenClaw 由编排器调用，自己不能调用它们。

7. Human-in-the-loop 迭代流程

agent 负责“多出候选、快出候选”，人负责“挑、批注、定稿”。每一步选定的结果都锁定进导演基准包，后面的生成只在基准上叠加，不再从头抽卡。

下一步输入的是上一步锁定的资产，所以越往后可变的东西越少，生成也越贵。人的判断因此要前置：在便宜的低分辨率阶段多挑，在昂贵的正片阶段少返工。

约束可配置

身份一致只是约束之一，所有约束都做成可配置项，而不是写死在流程里。每个约束有四个属性：是否开启、来源（参考图或基准包里的哪一项）、检查方式与阈值、不达标时的处理方式。开启一个约束，模板自动挂上对应的输入，检查环节加上对应的评分项；关掉它，相应的阶段和检查就跳过。例如不要求身份一致时，跳过定妆照，直接从风格探索进入样片。流程和组件不变，变的只是这次任务带哪组约束。

约束开启后挂到模板的输入检查项不达标时（可选）
身份一致定妆参考图人脸特征相似度仅提示 / 排序降权 / 自动重抽
风格一致风格参考图、色板、风格 LoRA图像嵌入相似度仅提示 / 排序降权
服装与场景一致服装、场景参考图视觉模型差异说明仅提示
输出规格分辨率档位、时长档位、帧率规格校验（确定性）拒绝提交
审阅点无哪些阶段需要人确认未确认不进入下一阶段
探索预算无轮数、时长、候选数上限到达上限即停并汇报

配置分三层，后者覆盖前者：项目默认值 → 任务文件或需求澄清时的选择 → 审阅中的临时调整。约束配置是任务记录的一部分，写入 manifest，结果可追溯到当时的设置。Telegram 用 /constraints 查看和修改，由监听器直接处理，不唤醒 LLM。

人的反馈动作

审阅时只提供四个动作，每个都对应编排器里一个确定的行为；自由文字批注由 agent 翻译成下一轮的参数改动。

动作含义系统行为
选中采纳这一张或一条锁定其种子、参数、参考图，写入基准包
微调重抽方向对，细节不对固定种子，小幅改参数或局部重绘
混合取 A 的构图 + B 的色调把 A、B 作为下一轮的参考图组合
打回 + 批注方向不对，附一句说明agent 改 prompt 或换模板/模型，重抽一轮

导演基准包内容

  • 角色与场景的定妆照（参考图）及其种子、prompt 片段、负面词。
  • 风格资产：风格参考图、色板、使用的模型与 LoRA 版本。
  • 视频参数：定稿样片的运动参数、镜头语言、时长档位。
  • 版本号与签字记录；修改基准包会生成新版本，老产物仍可追溯到当时的版本。

快速迭代的做法

  • 候选轮用预览档：低分辨率、少步数，每轮一组并排出图；只对选中的图做放大和精修。
  • 审阅会话期间保留模型加载（即释放策略里的“连续同模型保留”），反馈到下一轮出图不用重新加载。
  • 等人的时候不占 LLM：任务进入“待审阅”状态后编排器只是等待，长时间无人响应再释放内存。
  • 本地审阅台：编排器起一个轻量网页，候选以网格并排、可与基准包左右对照，支持键盘快捷键选择和手机上审阅；一组候选生成完发通知。

待定：每轮候选的数量和预览档的具体分辨率，取决于 G0 实测的单张耗时。

8. 验证计划与里程碑

先花最少的力气拿到最关键的数字：视频生成的峰值内存与模型切换耗时。它们决定 LLM 能否常驻、档位上限在哪里，也决定后面的阶段值不值得做。

每个阶段只在前一道闸门通过后开始；未给出具体日期，排期待定。与原计划相比：视频冒烟和切换耗时提前到阶段 0；图片闭环先用 CLI 跑通，再接 Telegram；搜索、Skills、MCP 从阶段 4 移到最后。若 G0 显示内存很紧，严格错峰就是必需；若切换耗时很长，审阅会话期间应让生成模型常驻。

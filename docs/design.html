Lightweight local video agent
Design doc: review, architecture and human in the loop

Based on the "Local takeover trial report (verified)" and "Lightweight local video agent · Implementation plan". Telegram + our own service are the main entry, a deterministic orchestrator owns every side effect, the LLM is woken on demand, and OpenClaw is a callable sub-agent.

1. Background and scope

Conclusion: using a local 27B model as the "control plane" and ComfyUI as the "execution plane" is workable, but so far only the easiest part has been proven (reading facts and writing a report). The real risks — autonomously editing workflows, video end to end, peak generation memory — are all unverified. Recommendation: take the LLM off the critical path first, build a deterministic orchestrator, then add the LLM as an optional planner.

This doc is based on the "Local takeover trial report (verified)" and "Lightweight local video agent · Implementation plan" (a draft plan, not yet implemented). Section 2 reviews the plan item by item; the remaining sections are design advice built on that review.

Facts confirmed by the trial

  • OpenClaw with lmstudio/qwen3.8-27b-splash completed one agent exec in 85.2 s, exit code 0, no --deliver, no paid fallback.
  • ComfyUI queue queries, /free when idle and refusing to release on a busy queue are verified; after /free the process RSS went from about 9.3 GiB → 0.82 GiB.
  • Total machine memory 128 GiB; ComfyUI reported about 58.9 GiB available, about 54 GiB system available after /free (affected by other processes).
  • The tooling is isolated in workflows/openclaw-local-media; no global config was changed, no resident components installed.

Not covered here: concrete model choice and quantisation, ComfyUI node-level tuning, fixing the SQLite warnings in OpenClaw's database.

2. Review of the implementation plan

The plan's core judgements are right: centre on a model scheduler, confirm releases, only touch our own models, start from an approved casting, leave final aesthetics to people. Three main problems: the scope is too big — it effectively rebuilds OpenClaw; strict staggering puts several model loads on every iteration, which conflicts with fast picking; and the biggest unknown (peak video memory) is only verified in stage 3.

What the plan does well

  • The state machine makes "release the control model" and "release the generation model" explicit states, and requires confirming releases with memory observations instead of trusting the API response.
  • Model ownership and "respect manual tasks" cover exactly the race in concern #5 below.
  • Saving ComfyUI job IDs for restart recovery avoids duplicate generation.
  • Candidate images distinguish "temporary experiments" from "user-approved casting", and each round starts from the approved baseline — consistent with this doc's director's baseline pack.
  • Every stage has completion criteria; the isolation (own directory, virtual environment, database, started by hand first) is sound.

3. Feasibility

Overall: feasible with conditions. "Serial + API-driven + templated parameters" has no technical obstacle; "the LLM autonomously edits and submits workflows" and "the LLM and the video model stay resident together" are two conditions that need measurements before any conclusion.

DimensionConclusionConfidenceBasis and gaps
Orchestration (ComfyUI API)FeasibleHigh/prompt, /queue, /history and /free are standard endpoints, queue and release logic measured; editing workflow JSON parameters by node ID is deterministic
LLM control plane (27B)Text tasks feasible; autonomous workflow editing unknownMedium → lowOnly "read facts, write a report" was verified; a local 27B editing node graphs directly is error-prone (wrong node IDs, type mismatches, out-of-range parameters)
Memory coexistenceUnknown, probably tightLow128 GiB unified memory, about 54 GiB available as measured later; actual LLM weight footprint not measured; peak video model memory not measured; the VM keeps about 14.7 GiB resident

Rough memory estimate (approximate, not measured): a 27B model is about 16–18 GiB at Q4 and 28–30 GiB at Q8; the report's "BF16 takes 54 GiB" has been marked unverified. With a resident Q8 LLM plus the VM and system overhead, maybe only 30–40 GiB remain for the video model — enough for short 640×384 videos but not generous. That is exactly the first number to measure.

The three biggest risks: the LLM is on the critical path of every step, memory coexistence is unmeasured, and the video path has never run end to end.

5. High-level design advice

Core advice: split the system into "a deterministic orchestrator + an optional LLM planner". The orchestrator does every operation with side effects; the LLM only translates natural-language requests into constrained plans; without the LLM the system still runs.

Design principles

  • Determinism first: submitting, polling, releasing and retrying are all done by Python code; the LLM never touches the ComfyUI API or a shell directly. (Revised 2026-11-07: the agent may request running commands, reading web pages, reading / writing files and using skills, executed by the orchestrator; commands need the user's approval per item by default, with "always allow" per kind or bypass mode; generation side effects still only go through the generation tools.)
  • Controlled exploration: the agent may explore different templates, models and workflows, but every new combination passes validation and a low-tier trial first; production tasks only use promoted templates.
  • Memory is a first-class resource: check available memory before every submit; the LLM and generation models take turns instead of aiming to stay resident together.
  • Every task is reproducible: parameters, seed, template version, constraint config, duration and peak memory go into the manifest, in the same directory as the outputs.
  • Least privilege: out-of-bounds behaviour is refused at the tool layer, not by prompt instructions.

Exploration: tiered, controlled exploration

The agent's exploration scope has five levels by risk, with heavier guard rails further down. The agent may do the first four on its own; only "promote to a real template" and "bring in new resources" need human confirmation.

LevelWhat the agent can doGuard railsHuman confirmation
L1 ParametersChange prompt, seed, sampler, steps, CFGSchema range constraintsNo
L2 TemplatesChoose and combine templates from the libraryTemplate registry, labelled with capabilities and use casesNo
L3 ModelsSwitch between local checkpoints, LoRAs and VAEsThe model registry records size and measured peak memory; memory gate before submittingNo
L4 WorkflowsAdd / remove nodes, rewire, write new workflowsNode types and links validated against ComfyUI /object_info; trial at the lowest tier; outputs written to a sandbox directoryWhen promoting to a real template
L5 New resourcesDownload models, install custom nodesKeep the trial report's constraints: no downloads, no resident components by defaultEvery time

Life cycle of a new workflow: candidate → graph validation → lowest-tier trial → evaluation → promoted into the template library after human confirmation. Every exploration writes an experiment record (template, model, change, duration, peak memory, result score); the agent checks these records before exploring again to avoid repeating mistakes.

Exploration needs a budget: each round limits the number of trials or the total time, because one video trial on a Mac takes minutes, plus about 85 s per 27B turn. Evaluating results is an open point: human scoring is most reliable, automatic scoring by a vision model takes another chunk of memory.

Wake on demand: the LLM is not resident and starts when a message arrives

Only a message listener that loads no model stays resident. It handles commands and buttons itself; only free text that needs understanding loads the LLM, which then starts an idle timer and unloads when it expires. People can step in any time without the memory cost.

Message typeExampleWakes the LLMHandling
Command/status, /cancel, /pause, /budgetNoExecuted by the listener directly
Button choicePick #2, reject, mix 1+3NoWrites the review result, triggers the lock or the next round
Free-text note"Make the eyes a little sadder, light from the side"YesUnderstood as parameter changes, submitted after validation
New request"Make a looking-back shot from this casting photo"YesFirst clarify key options (identity consistency or not, duration, style), then plan tasks
  • Cold starts are slow: loading the 27B reads all its weights, plus inference (measured 85.2 s per turn), so a free-text message may take a minute or two to answer. The listener replies "got it" right away.
  • An idle timer avoids repeated loads: consecutive messages share one load; the timer length follows the load time measured in G0. Whether LM Studio's on-demand load and idle auto-unload work per instance is to be verified in stage 0.
  • Several messages arriving during a load are handled together.
  • No preemption of generation: while generation holds memory, free text queues; urgent instructions like "stop" or "cancel" are commands executed by the listener immediately, without waiting for the LLM. If G0 shows memory headroom, the LLM may coexist with generation.
  • Context is rebuilt from the database: each wake-up reads the project summary, baseline pack and recent records, never replaying the whole chat.
  • Background exploration works the same way: the scheduler only wakes the LLM when the next round needs planning; user messages take priority over the next exploration round.

Residency modes: optional, wake on demand by default

How the LLM stays resident is a switchable option. Switching uses the /mode command, executed by the listener without the LLM; each project can also have a default.

ModeLLM behaviourFitsCost
Wake on demand (default)Loads only on free text, unloads when the idle timer expiresEveryday use, left running for long periodsEvery cold start waits a minute or two
Session residentStays loaded after /session starts, unloads at the end or on timeoutIntensive picking, consecutive notesHolds memory during the session; generation must coexist or queue

The memory gate takes precedence over the mode: when a generation task needs memory that cannot fit alongside a resident LLM, the scheduler unloads the LLM temporarily and tells the user over Telegram; after generation it is restored per the original mode.

OpenClaw as a callable sub-agent

Decided: the main entry is Telegram + our own service, and scheduling authority lies with the orchestrator. OpenClaw becomes a sub-agent the orchestrator calls on demand, providing abilities we do not want to build (search, existing skills, MCP). Review problem #1's scope creep is largely resolved by this.

6. Target architecture

(2026-11-07: the OpenClaw sub-agent design in this section is superseded by §6b.) Two entries flow into one orchestrator; the LLM planner is optional; neither Telegram nor the LLM can reach ComfyUI or a shell, and OpenClaw is called by the orchestrator on demand.

A task's life cycle: draft → validated → waiting for memory → submitted → running → review → done / rejected / failed / timeout. Every state change is written back to the manifest; after a process restart, reconcile by prompt_id against /history to avoid duplicate submits.

The orchestrator exposes only four commands: plan (optional, asks the LLM for parameters), submit (validate and submit), status (query tasks), release (release when idle). The Telegram listener can only call these four; OpenClaw is called by the orchestrator and cannot call them itself.

6b. Today: the general agent architecture (2026-11-07)

§6's "OpenClaw sub-agent provides search / skills / MCP" has been superseded: the orchestrator now executes these abilities itself (user decision 2026-11-07). The LLM is the brain and only proposes tool calls; the orchestrator is the hub that executes every tool and hands results back to the LLM as memory allows.

  2. Less approval friction: done — approval buttons gained "Always allow" (rules per program / MCP tool / delegate), /permissions bypass skips everything; hard refusals still apply, installing nodes / downloading models still asks every time.

  4. Controlled self-extension: let the agent propose new templates (e.g. generated from a ComfyUI workflow), registered after the orchestrator validates them, trial-runs at the lowest tier and you approve.

7. Human-in-the-loop iteration

The agent's job is "more candidates, faster"; the person's job is "pick, annotate, sign off". Each step's picked result is locked into the director's baseline pack, and later generation only builds on that baseline instead of rolling the dice from scratch.

Each step's input is what the previous step locked, so less and less can vary further on, while generation gets more expensive. Human judgement should therefore come early: pick a lot in the cheap low-res stages, rework little in the expensive final stage.

Configurable constraints

Identity consistency is only one constraint; every constraint is a configurable item rather than hard-wired into the flow. Each constraint has four properties: on or off, source (which reference image or baseline pack item), check method and threshold, and what to do when it fails. Turning a constraint on attaches the corresponding inputs to the template and adds the matching score to the checks; turning it off skips the related stage and checks. For example, without identity consistency, skip casting and go from style exploration straight to test clips. Flow and components stay the same; only the set of constraints a task carries changes.

Config has three layers, later ones overriding earlier ones: project defaults → the task file or choices made when clarifying the request → temporary adjustments during review. The constraint config is part of the task record and written into the manifest, so results trace back to the settings of the time. Telegram views and edits it with /constraints, handled by the listener without waking the LLM.

The person's feedback actions

Review offers only four actions, each mapping to one deterministic orchestrator behaviour; free-text notes are translated by the agent into the next round's parameter changes.

ActionMeaningSystem behaviour
PickTake this image or clipLock its seed, parameters and reference images into the baseline pack
RefineRight direction, wrong detailsFix the seed, small parameter changes or local inpainting
MixA's composition + B's tonesCombine A and B as the next round's reference images
Reject + noteWrong direction, with a one-line explanationThe agent changes the prompt or the template / model and redoes the round

What the director's baseline pack contains

  • Casting images (reference images) of characters and locations, with their seeds, prompt snippets and negative terms.
  • Style assets: style reference images, palette, the models and LoRA versions used.
  • Video parameters: the signed-off test clip's motion parameters, shot language and duration tier.
  • Version numbers and sign-off records; changing the pack creates a new version, and old outputs still trace back to the version of their time.

How to iterate fast

  • Candidate rounds use the preview tier: low resolution, few steps, one set side by side per round; only the picked image is upscaled and refined.
  • Keep the model loaded during a review session (the release policy's "keep for consecutive same-model tasks"), so the next round after feedback needs no reload.
  • No LLM while waiting for people: once a task enters "review", the orchestrator just waits, and releases memory after a long time without a response.
  • Local review page: the orchestrator serves a light page with candidates in a grid, comparable side by side with the baseline pack, keyboard shortcuts for picking and usable on the phone; a notice goes out when a set of candidates is ready.

Open: the number of candidates per round and the exact preview-tier resolution depend on the per-image time measured in G0.

8. Verification plan and milestones

First get the most important numbers with the least effort: peak memory of video generation and model switch times. They decide whether the LLM can stay resident and where the tier ceiling is, and whether the later stages are worth doing.

Each stage starts only after the previous gate passes; no dates are given, scheduling is open. Compared with the original plan: the video smoke test and switch times move up to stage 0; the image loop runs through the CLI first, then Telegram; search, skills and MCP move from stage 4 to the end. If G0 shows memory is tight, strict staggering is required; if switching is slow, the generation model should stay resident during review sessions.

9. Open questions

  • Decided: Telegram + our own service as the main entry, OpenClaw as a callable sub-agent. To verify: can the OpenClaw gateway start and stop on demand, and share the same model instance with this service?
  • Which model and precision does the video workflow use? That sets the upper bound of the memory budget.
  • What are the 27B control model's actual quantisation and loaded footprint?
  • Decided: whether identity consistency is needed is clarified per task when the user makes a request, as a configurable constraint that does not affect the architecture.
  • Expected usage: how many tasks a day, how long a single task may take, whether to batch overnight?
  • Will the user use ComfyUI by hand while the system runs? That decides whether the release policy can be automatic.
  • Must the VM (about 14.7 GiB) stay resident?
  • If the requests themselves are quite fixed, is the LLM really needed? Templates + CLI may be enough.
